# Where Pretzel is used

Every Pretzel module, what it does in this game (or why it is not here), and where to read it. Paths are relative to `Assets/_Scripts/Runtime` unless they start with `_Project`. To find all uses of a module, search for its namespace, for example `using Pretzel.Pooling`. Each module name links to its package README, which has the full API.

**How to follow this page**

1. Read [Follow one shot](#follow-one-shot) first. It walks a single bullet through the modules and shows how they fit together.
2. Use [At a glance](#at-a-glance) to find the module you care about and open its file.
3. Read [Modules this game does not use](#modules-this-game-does-not-use) for the five packages that are not in the game's code (Cloud, Api, UI (UGUI), Integrations and Editor), and for where each would plug in.

## Follow one shot

The player presses fire and the bullet kills an invader. Every step is one Pretzel module doing one job.

| Step | What happens | Module | File |
|---|---|---|---|
| 1 | The `Player` input context is on top of the stack and the scene-load gate is open, so the fire action is live | [Inputs](../../../Packages/com.uee03.pretzel.input/README.md) | `Composition/GameInput.cs` |
| 2 | `ShipControls` reads the fire action and `PlayerShip` asks its `Cooldown` whether it may shoot | [Core](../../../Packages/com.uee03.pretzel.core/README.md) | `Gameplay/Actors/PlayerShip.cs` |
| 3 | The ship takes a bullet from the pool and publishes `PlayerFired` | [Pooling](../../../Packages/com.uee03.pretzel.pooling/README.md), [Events](../../../Packages/com.uee03.pretzel.events/README.md) | `Gameplay/Actors/ProjectileSpawner.cs` |
| 4 | `GameAudioReactions` hears `PlayerFired` and plays the laser by id | [Sfx](../../../Packages/com.uee03.pretzel.sfx/README.md) | `Audio/GameAudioReactions.cs` |
| 5 | The bullet's trigger hits an `Invader`, which raises `Killed`. `InvaderFormation` publishes `InvaderDestroyed` and releases the invader to its pool | [Pooling](../../../Packages/com.uee03.pretzel.pooling/README.md), [Events](../../../Packages/com.uee03.pretzel.events/README.md) | `Gameplay/Actors/Projectile.cs`, `InvaderFormation.cs` |
| 6 | `LevelPresenter` adds the score. `GameService` raises `ScoreChanged` and the HUD redraws | [UI](../../../Packages/com.uee03.pretzel.ui/README.md) | `Gameplay/Level/LevelPresenter.cs`, `UI/HudPresenter.cs` |
| 7 | `GameFeelReactions` freezes the game for a few frames and nudges the camera | [Vfx](../../../Packages/com.uee03.pretzel.vfx/README.md), [Cameras](../../../Packages/com.uee03.pretzel.camera/README.md) | `Feel/GameFeelReactions.cs` |
| 8 | `ExplosionSpawner` takes an explosion from the pool and `ExplosionFx` grows and fades it with easing | [Pooling](../../../Packages/com.uee03.pretzel.pooling/README.md), [Tween](../../../Packages/com.uee03.pretzel.tween/README.md) | `Gameplay/Actors/ExplosionSpawner.cs`, `ExplosionFx.cs` |
| 9 | If it was the last invader, `LevelPresenter` starts the next wave and `WaveStarted` shows a toast. The star field scrolls a little faster | [UI](../../../Packages/com.uee03.pretzel.ui/README.md), [Parallax](../../../Packages/com.uee03.pretzel.parallax/README.md) | `Gameplay/Level/LevelPresenter.cs`, `Feel/GameFeelReactions.cs` |
| 10 | When the game ends, the high score is saved to disk | [Data](../../../Packages/com.uee03.pretzel.data/README.md) | `Composition/GameService.cs`, `Composition/SaveService.cs` |

Every object above received its dependencies from a scope instead of looking them up ([VContainer](../../../Packages/com.uee03.pretzel.vcontainer/README.md), generated by [Setup](../../../Packages/com.uee03.pretzel.setup/README.md)). Steps 4, 6, 7 and 8 never call the ship or the bullet: they only listen for an event, which is why [feel is a reaction, not game logic](#things-worth-knowing). In co-op the same events still drive the reactions, and the host forwards them to the other player's machine: see [Multiplayer](#multiplayer).

## Setup

- **Folder preset.** *Pretzel > Create > Folders* made the layout described in the README: scripts under `_Scripts`, everything else under `_Project`.
- **VContainer tab.** It generated `GameInstaller.Generated.cs`, `GameInstaller.cs`, `GameFlow.cs`, the starter `ISaveService`, `SaveService`, `IGameService`, `GameService`, `GameState` and `GameProgress`, and the `GameNavigator` service shell, then created the scope prefab, the installer asset and `VContainerSettings`. Only `GameInstaller.Generated.cs` is machine-owned. The saved choices are in `ProjectSettings/Pretzel/pretzel-settings.json`.
- **Scripted setup.** The same generation runs headless, which is how this project was set up: `Unity -batchmode -projectPath . -executeMethod Pretzel.Setup.PretzelSetupBatch.Composition` (do not pass `-quit`). See the Setup README.
- **Scene template.** `Editor/SceneBuilder.cs` creates both scenes from *Pretzel 2D*, so they start with the `[CAMERA]`, `[ENVIRONMENT]`, `[MANAGERS]` and `[UI]` groups.

## VContainer module

- `GameInstaller` is a `ScriptableInstaller`: registrations kept in an asset that applies to the whole project.
- `LevelInstaller` and `TitleInstaller` are `MonoInstaller`s: registrations that need references to objects in one scene.
- The root scope prefab and both scene scopes are `PretzelLifetimeScope` components, which register the settings assets and run the installers.

## Core

- `Cooldown`: the player's fire rate (`PlayerShip.TryFire`) and the gap between invader bombs (`InvaderFormation.TryDropBomb`).
- `CountdownTimer`: the march step (`InvaderFormation`), the mystery ship's next appearance (`UfoSpawner`) and the ship's invulnerability after a hit (`PlayerShip`). The owner ticks it, so pausing (`Time.timeScale = 0`) needs no extra code.
- `FrameBudget`: spreads the pool prewarm over several frames (`InvaderFormation.PrewarmAsync`).
- `Guard.NotNull`: validates what `[Inject]` methods receive.
- `CompositeDisposable` and `AddTo`: one bag for each class's event subscriptions (`GameAudioReactions`, `HudPresenter`, `LevelPresenter`, `ExplosionSpawner`).

## Events

`EventBus` is registered as `IEventBus`. Messages are `readonly struct`s in `Gameplay/Messages/`. See the [event table](Architecture.md#the-event-bus) for who publishes and who listens.

## Pooling

| What | How | File |
|---|---|---|
| Bullets and bombs | `PoolFactory<ProjectileKind, Projectile>` as a serialized field, prefabs and prewarm set in the Inspector | `Gameplay/Actors/ProjectileSpawner.cs` |
| Co-op bullets and bombs | Network prefabs listed under *Pooled Prefabs* on `PretzelNetworkBootstrap`; the pooled spawn handler recycles them on the host and on every client | `Coop/Actors/CoopProjectileSpawner.cs` |
| Invaders | `PoolFactory<InvaderKind, Invader>`, prewarmed behind the loading screen | `Gameplay/Actors/InvaderFormation.cs` |
| Explosions | `IPoolRegistry` from the container, one pool per prefab | `Gameplay/Actors/ExplosionSpawner.cs` |

`Invader`, `Projectile` and `ExplosionFx` implement `IPoolable` to reset themselves, and release through the `PooledObject` that the pool adds. Shooters depend on `IProjectileSpawner`, not on a prefab.

## Scenes

- `GameNavigator` builds a `SceneLoadOptions` with a transition, a minimum duration, `SceneProgressWeight`, a status line, a `SetupAsync` callback and a `FallbackScene`. The loader's `RequestPolicy` is `Ignore`, so a double click on Play does nothing.
- `LevelSetup.PrepareAsync` is the `SetupAsync` work: it reports status and prewarms the invaders with the loader's progress. `GameNavigator` finds it with `SceneSetupContext.FindInScene<T>()`.
- The loading screen is a `UIDocumentSceneTransition` on a child of the root scope prefab, built from `_Project/UI/Layouts/Loading.uxml` (a `status` label and a `progress` bar). It stays in place because its parent already survives scene loads.

## UI

- `HudView` and `TitleView` derive from `UIControllerBase`: they query elements in `OnBind` with `QRequired<T>`, hook buttons with `OnClick` and sliders with `OnValueChanged`, and release them in `OnUnbind`.
- `HudView` uses a `UIScreenStack` with modal pushes for the pause and game-over overlays, and a `ToastService` for wave and mystery-ship messages.
- The layouts use `SafeAreaElement`. The USS (`_Project/UI/Styles/SpaceInvaders.uss`) follows the BEM naming rules and also restyles `pretzel-toast` to show that your own rules override the toast default.
- Presenters (`HudPresenter`, `TitlePresenter`) hold the logic. The views only expose events and setters.

## Audio

`AudioService` is a child object of the root scope prefab (Setup adds it) and is registered as `IAudioService`. `SoundBank` holds the four march clips, which play straight through `IAudioService`, and the three music clips. `GameFlow` pushes the saved volumes to the `Master`, `Music`, `Sfx` and `UI` channels.

Music uses `IAudioService.PlayMusic`, which crossfades between two looping sources on the Music channel. `TitleMusic` (an entry point of the title scope) plays the title tune. `GameMusic` (an entry point of the level scope) starts the gameplay loop, switches to the last stand from wave 5 (`SoundBank.LastStandFromWave`), and fades out on `GameEnded`. It plays the first wave's tune from `Start`, because the first `WaveStarted` can be published before it subscribes. The clips import as streamed Vorbis (`SoundBankBuilder`).

## Sfx

Everything except the march is played by id. `GameSounds` holds the id constants, `SfxLibrary` (an asset on the root scope prefab, built by **Rebuild Sound Library**) maps each id to a cue, and `GameInstaller` registers `SfxPlayer` as `ISfxPlayer`. `GameAudioReactions` calls `_sfx.Play(GameSounds.InvaderDestroyed)` and so on, and the player's throttle keeps a mass kill from stacking voices.

## Vfx

`TimeScaleService.Instance` is registered as `ITimeScale`. `GameFeelReactions` asks it for a `Freeze` on every kill and a `SlowMotion` when the ship is hit or the game ends. Pause sets `Time.timeScale` to 0 and the service treats that as the new baseline, so effects never un-pause the game. The player prefab has `SpriteFlash` (red flash) and `PunchScale`, both triggered from `GameFeelReactions`.

## Cameras

`SceneBuilder` creates the camera with `CameraRigBuilder.Create`: a Cinemachine Brain, a virtual camera, `CameraShake` and `PlayfieldFitter` (Contain, 17.8 by 10). `LevelInstaller` registers the `CameraShake` as `ICameraShaker`, and `GameFeelReactions` adds trauma on each event. The fitter makes the whole playfield visible on any aspect ratio.

## Parallax

Three star layers (`ParallaxLayer`, 4 by 4 tiled sprites from `_Project/Art/Stars`) sit under one `ParallaxController` and auto-scroll at 0.35, 0.9 and 1.8 units a second. The camera is static, so the scroll comes from `AutoScroll`. `GameFeelReactions` raises `SetAutoScrollScale` a little on each wave. The layers use scaled time and stop on pause.

## Inputs

`GameInput` is an entry point that builds an `InputRouter` over `InputSystem.actions`. The `UI` map is always on; `Player` is a context that is pushed on start. `Pause()` pushes the empty `Paused` context so the ship stops while the pause menu works, and `Resume()` pops it. `SceneLoadInputGate` blocks input while a scene loads. `InputDeviceTracker` records the last device used. `LevelPresenter` calls `Pause` and `Resume`, and `ShipControls` only reads values. The co-op ships do not use the router: `CoopShipInput` reads the keyboard and the gamepads directly, one scheme for each local player index, because two players on one machine need two schemes at once.

## Data and Preferences

- `SaveService` is the only class that touches `IDataStore` (`DataIO.Default`, plain JSON). A corrupt file throws and is kept, never overwritten.
- `GameService` loads `GameProgress` once through `LoadProgressAsync`, raises `ProgressLoaded` and saves the high score at the end of a game. Progress is not saved if loading failed.
- `GameFlow` is an `IAsyncStartable`: it loads preferences first, applies them to the audio channels, then loads progress. `MasterVolumeSetting` changes the master volume with `PreferencesService.Modify` and saves.

## Multiplayer

The **Coop** scene (the title's CO-OP button) plays the same game for two people, on one machine or online. The Pretzel Multiplayer package runs the session; a small set of game classes in `Assets/_Scripts/Coop` (assembly `SpaceInvaders.Coop`) does what is specific to Space Invaders. The single-player assembly has no netcode references, and its code path is unchanged.

**What the package provides, and where the game uses it**

| Pretzel Multiplayer piece | Where the game uses it |
|---|---|
| `PretzelNetworkBootstrap` | On the `Network Manager` object in `Coop.unity`. Settings: two players, up to two on one machine. The player prefab is `CoopShip`, with two spawn points. *Pooled Prefabs* lists the bullet and the bomb |
| `IMultiplayerSessionService` | `CoopMatchDirector` begins the match when `StateChanged` reports `Playing` and returns to the lobby when it leaves it. `CoopHudPresenter` calls `LeaveAsync` and `EndMatchAsync` |
| `MultiplayerMenu` | The drop-in menu, unchanged: local co-op, host online, join with code, quick join, the lobby and the rejoin prompt |
| `PooledNetworkPrefabHandler` | Recycles bullets and bombs on the host and on every client |
| `NetworkPlayerIdentity` | On the ship. The slot picks the colour and the stats; `LocalPlayerIndex` picks the controls |
| Slots, connection approval, rejoin | Not touched. A player who rejoins within the grace window gets the same ship, lives and score back |

**What the game adds**

| Class | What it does |
|---|---|
| `CoopRunState` | The rules, in plain C#: lives and score for each player, game over when everyone is out |
| `CoopMatch` | The shared state (phase, wave, each player's stats) and the hub that ships and projectiles find. It also forwards the host's game events to clients, so each client's own event bus drives audio, explosions, toasts and shake |
| `CoopWorldReplicator` | Copies the host's invaders, mystery ship and bunker wear into compact replicated values. Clients apply them to the same scene objects with their simulation off |
| `CoopMatchDirector` | The host's rules: waves, lives, score, game over. The counterpart of `LevelPresenter`; on a client it does nothing |
| `CoopShip` | One player's cannon. Moves where its owner puts it; the host validates every shot and decides every hit |
| `CoopProjectile`, `CoopProjectileSpawner` | Pooled network bullets and bombs. The invader formation spawns bombs through the same `IProjectileSpawner` interface it uses in single player |
| `CoopHudView`, `CoopHudPresenter`, `CoopFeelReactions` | A score bar for each player, the game-over panel and leave buttons; camera shake and star-field speed |
| `CoopNetworkLifetime` | Destroys the `NetworkManager` when the scene unloads (see below) |

**Who decides what**

| Thing | Decided by | How the others see it |
|---|---|---|
| Where a ship is | Its owner (owner authority) | `NetworkTransform` |
| Firing | The owner asks, the host decides: the ship is alive, the match runs, the cooldown is over | A bullet appears everywhere |
| Bullets and bombs | The host spawns and removes them | Pooled network prefabs. Every machine flies them in a straight line from the spawn point, so nothing is sent while they fly |
| Hits, lives, score, waves, game over | The host only | `NetworkVariable`s and a `NetworkList` on `CoopMatch` |
| Invaders, mystery ship, bunkers | The host simulates them | One `FormationSnapshot` per march step or kill (an alive mask, not 55 transforms), a `UfoSnapshot`, and a list of brick health values |
| Sound, explosions, toasts, shake | Each machine, from events the host forwards | `PlayerFired`, `InvaderDestroyed`, `PlayerHit`, `UfoDestroyed`, `WaveStarted` and the like, sent as RPCs to clients and published on their own bus |

Movement is owner-authoritative, so a client that wants to cheat can place its own ship anywhere; the host only clamps where a shot starts. That is a fair trade for a game between friends and it keeps the controls free of latency. Everything that matters for the score is the host's.

**The rules in co-op.** Each player has three lives and their own score. The game is over when both players are out of lives, or when the invaders land. A player who leaves for good (the reconnect grace window runs out) is dropped from the rules, so they cannot hold the match open. Only two players take part: a third ship (two on one machine plus a remote player) sits out. The host can send everyone back to the lobby for a new match. There is no pause, no hit stop or slow motion (they change `Time.timeScale`, and one player's freeze must not slow the host's simulation for everyone), no dev console, and the high score is not saved. Press **Quit to title** to go back to the title.

**Things worth knowing**

- **The event RPCs are host-only.** NGO's default RPC permission is *Everyone*, which would let a modified client invoke `GameEndedRpc` or `InvaderDestroyedRpc` and have the host relay the forged event to the others. They are declared with `InvokePermission = RpcInvokePermission.Server`. `FireRpc` is the only RPC a client may send, and only the ship's owner.
- **A wave can have at most 128 invaders**, one bit each in the formation snapshot. `CoopMatchDirector` refuses a larger wave with an error instead of letting clients lose invaders the host still simulates.
- **NGO keeps its `NetworkManager` across scene loads.** It is marked `DontDestroyOnLoad`, so leaving the Coop scene would leave the old manager behind and the next visit would create a second one. `CoopNetworkLifetime` ties the manager to the scene.
- **A `NetworkManager` cannot be nested under another object.** `SceneBuilder.Coop.cs` keeps it, and the in-scene `Coop` object, at the scene root.
- **A repeated Editor build must not register a prefab twice.** `NetworkPrefabListUtility.Register` was fixed for this: a duplicate prefab entry gave NGO a `GlobalObjectIdHash` error at runtime.
- **Your Unity Cloud project link stays out of git.** Linking the project writes your project id into `ProjectSettings/ProjectSettings.asset`. `.gitattributes` runs a filter that blanks those lines on commit, and `.githooks/pre-commit` refuses a commit that still has them. Enable the filter once per clone: `git config filter.unity-cloud-link.clean "sed -E 's/^(  (cloudProjectId|projectName|organizationId):)[^\r]*/\1 /'"`.
- **Online play needs a linked Unity Cloud project** with Authentication and Multiplayer Services (Relay) enabled. To play against yourself on one machine, give each copy a different *Authentication Profile* in the bootstrap settings.
- **Try it in the Two Cubes sample first** if you are new to the package: it is the smallest example of a player prefab, local input mapping and pooled spawns.

## DevConsole

`DeveloperConsole` is a component in the Game scene (back-quote to open). `DevCommands` registers `god`, `score`, `lives`, `wave`, `clear` and `ufo` on its `CommandRegistry`, and removes them when the level scope is disposed.

## Tween and Extensions

`MarchTempo` uses `EaseUtility.Lerp(EaseType.InQuad, ...)` so the march speeds up faster as the formation thins out. `ExplosionFx` grows with `OutCubic` and fades with `InQuad`. `InvaderFormation` picks the bomber with `GetRandomItem()`.

## Editor tooling

`WaveDefinitionEditor` derives from `InspectorBase` and uses `EditorUI` (`Section`, `Row`, `Help`, `Separator`) for a live formation preview and warnings. The builder under `Editor/` is covered in [Build it yourself](BuildItYourself.md#editor-tools).

## Things worth knowing

- **Feel is a reaction, not game logic.** `GameFeelReactions` and `GameAudioReactions` only listen to events. Delete them and the game still plays, only flatter.
- **Input ownership is in one place.** `GameInput` enables and disables the action maps. `Gameplay/Actors/ShipControls.cs` only reads values from Unity's project-wide actions.
- **`RebindSession` is not used.** The game has no rebind screen; the Inputs package sample shows one.
- **The object that awaits a scene load must outlive it.** That is why `GameNavigator` is in the root scope rather than in a scene.
- **Scene components get dependencies by method injection.** An `[Inject]` method runs when the scope builds, before the component's `Awake`, so these methods only store what they receive.
- **Starter code is yours.** The generated services were edited freely; the only file Setup rewrites is `GameInstaller.Generated.cs`.
- **Play Mode keeps the template's default of no domain reload.** The game therefore holds no mutable static state: everything lives in scopes and components, so each Play session starts clean.
